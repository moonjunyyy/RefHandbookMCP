# 사이트 프레임 — 상속·활성·위젯·UI 규칙 (2026-11-01)

기준 문서. 사이트의 모든 화면과 앱이 공유하는 것(프레임)이 무엇이고 어디서 오는지, 사람의 것(테마·언어·켠 앱·홈)이 어떻게 모든 앱에 닿는지, 앱이 홈에 무엇을 올리는지, 화면 요소를 낳는 규칙이 무엇인지를 한 번에 정한다. 캘린더·볼트는 이 관례 안에서의 자리만 정하고 백엔드는 `docs/projects.md` 의 단계 3·4 가 만든다.

## 0. 상속과 기여
<!-- sec:s0 basis: U1 U2 A1 U9 E15 E20 -->

테마 토큰·공통 부품·프레임 코드의 주인은 로그인 서비스다. 사이트 화면과 호스팅 앱은 같은 계정 설정을 읽고, 앱은 기능과 자체 부품만 더한다. 모양 선택은 `deploy/site.toml [look]`, 사용자 설정은 `/apps/site/api/store/prefs`에 둔다.

앱은 선언에 위젯을 기여하고, 홈은 사람이 켠 앱의 위젯을 배치한다. 위젯 모듈이 제 서비스의 API를 부르므로 프레임에는 앱별 데이터 처리가 없다. 새로운 테마나 안내를 위해 프레임에 앱 이름을 하드코딩하지 않는다.

## 1. 공유 프레임과 테마 계약
<!-- sec:s1 basis: A1 A6 C1 E1 U9 E14 E15 E16 E17 E19 E20 H10 -->

| 파일·소스 | 계약 |
|---|---|
| `theme.css` | 두 모드의 색·글꼴·크기·간격·모서리 토큰 |
| `background.css` | 이미지 전용 배경층. 흐림·어둡기는 이 층에만 적용 |
| `guide.css` | 프레임을 쓰는 화면과 자체 부품을 쓰는 앱의 공통 안내 |
| `chrome.css` | 모든 화면의 사이트 머리글(이름·앱·내 메뉴·사용 안내). `body > header` 에만 걸린다 |
| `widgets.css` | 위젯이 그리는 공통 부품(항목 목록·숫자·진행 막대·날 띠·달·막대·활동). §4.2 |
| `parts.css`·`style.css` | 토큰으로 그리는 부품과 호환 진입점 |
| `theme.js` | 쿠키와 모양 캐시(토큰, 고른 열린 글꼴의 스타일시트)를 첫 칠 전에 적용 |
| `web/fonts.json` → `/apps/site/fonts/` | 사이트가 직접 싣는 열린 글꼴(OFL). §1.3 |
| `web/frame/` → `site.js`·`site.d/` | 계정 설정, 요소·부품·위젯·안내의 공통 API |

프레임의 공개 계약은 토큰 이름, 부품 클래스, ESM export다. 깨뜨리는 변경은 버전 경로를 나눠 제공한다. `npm run build`는 프레임 JS와 타입 선언도 생성하며, 설치본을 위해 이 산출물은 소스와 함께 반환한다.

### 색·글꼴·모서리

표면은 `--bg/--card/--soft`, 글자는 `--text/--muted`, 경계는 `--line`, 링크는 `--accent`, 상태는 `--ok/--warn/--bad`다. 사용자 강조색의 정확한 채움은 `--accent-fill`, 그 위 글자는 `--accent-fill-text`다. 링크용 `--accent-text`와 혼용하지 않는다.

선언된 팔레트는 밝음·어두움별 값을 가진다. 설정의 색상 선택기와 HEX 입력은 두 모드의 배경·본문·보조 글자·테두리·버튼·링크·상태색을 각각 편집하고 저장 전 미리 보여준다. 3자리와 6자리 HEX를 정규화한다. 지정한 배경과 버튼 채움은 유지하고, 공통 전경은 대비 4.5 이상이 되도록 조정한다. 한 공통 전경으로 읽을 수 없는 표면 조합은 저장 전에 거부한다.

둥글기 0–100은 카드 최대 24px, 컨트롤 최대 10px로 변환한다. 부품은 크기에 맞게 제한한 `--panel-radius/--control-radius/--grid-radius`를 사용한다. 글자 크기는 `--root-size`를 따른다.

### 글꼴 (§1.3)

본문·제목·코드의 글꼴은 각각 `--sans/--serif/--mono` 이고, 사람은 셋을 따로 고른다(사이트 파일 `[[look.type]]`·`[[look.heading]]`·`[[look.mono]]`). 각 토큰은 theme.css 에서 첫 글꼴과 대체 목록으로 나뉜다(`--sans: var(--sans-default)`, `--sans-default: "Plus Jakarta Sans", var(--sans-fallback)`). 선택지는 자기 글꼴을 앞에 두고 같은 대체 목록을 잇는다(`sans = '"Pretendard Variable", var(--sans-fallback)'`). 각 종류의 첫 선택지는 theme.css 그대로이고, theme.css 가 앞에 둔 글꼴이 열린 글꼴이면 그것을 불러온다(Plus Jakarta Sans·고운바탕·JetBrains Mono) — 고르지 않은 종류는 첫 선택지다. 토큰은 몸 글꼴 → 제목 → 코드 순으로 얹혀, 고른 제목 글꼴이 본문 선택지가 말한 `--serif` 를 이긴다.

글꼴 파일은 사이트가 직접 싣는다. `web/fonts.json` 이 열린 글꼴(OFL)마다 id·글꼴 이름·npm 패키지·가져올 CSS·라이선스를 선언하고, `npm run build`(`build:fonts`, `web/scripts/fonts.mjs`)가 패키지의 `@font-face` 를 읽어 woff2 만 남기고(unicode-range 조각은 그대로) 이름을 선언대로 붙여 `dist/fonts/<id>.css` 와 `dist/fonts/<id>/`(파일과 라이선스)를 만든다. 페이지 앱이 dist 를 `/apps/site/` 에 내므로 같은 출처이고 CSP(`default-src 'self'`) 안이다. 선택지는 `fonts = [id…]` 로 필요한 글꼴을 이름으로 부르고, 사이트 파일 `[look] fonts` 가 그 주소의 뿌리다. 프레임은 고른 선택지의 스타일시트만 `<head>` 에 `link[data-look-font]` 로 붙이고(theme.js 가 첫 칠 전에, site.js 가 바뀔 때), 브라우저는 그 글꼴 중에서도 글이 쓰는 조각만 받는다. 설정의 글꼴 목록은 갈래(고딕·명조·손글씨·제목용·고정폭 — `portal/site.py` FONT_GROUPS)로 묶고 줄마다 그 글꼴로 쓴 견본을 보이며, 견본의 글꼴은 줄이 보일 때 불러온다. 앱은 글꼴 출처를 쓰지 않는다 — 글꼴은 프레임이 붙인다.

### 배경과 저장

이미지는 같은 사이트 경로나 HTTPS 주소를 받아 읽을 수 있는지 확인한다. 흐림 0–30px와 어둡기 0–100%는 이미지에만 적용하며 내용 표면은 읽힘을 유지한다. 드래그 중에는 미리보기에만 반영하고, 계정 저장 성공 뒤 본문과 첫 칠 캐시를 바꾼다. SSO의 `default-src 'self'` 아래에서는 외부 이미지가 차단될 수 있다.

### 머리글은 프레임의 것: 모든 화면, 모든 앱

사이트의 머리글(사이트 이름, 사람이 켠 앱, 내 메뉴와 그 안의 사용 안내)은 프레임이 그린다. 사이트 화면과 호스팅 앱은 똑같이 `chrome()` 한 번을 부른다: 페이지에 머리글 골격(`<header>` 안의 `#brand`·`#nav`)이 있으면 그것을 채우고, 없으면 페이지 맨 위에 만든다. 앱은 자기 내용과 자기 조작만 더한다 — 사이트 경로로 가는 링크 줄, 머리글, 사용 안내 단추, 글꼴 출처를 앱이 쓰지 않는다. 글꼴은 토큰(`--sans/--serif/--mono`)이 이름을 정하고, 웹 글꼴은 사람이 고른 사이트의 열린 글꼴만 프레임이 붙인다(§1.3).

자체 부품을 쓰는 앱(WordGenerator)은 `theme.css`·`chrome.css`·`guide.css`·`background.css` 를 빌드에 포함하고, 자체 Tailwind 클래스를 색 이름 대신 표면·본문·동작·상태 역할에 연결한다. 앱 자신의 머리 줄(제목·탭·동작)은 사이트 머리글 아래의 페이지 머리이고, 고정(sticky)되지 않는다. 독립 실행(프레임 없음)에서는 글쓰기와 브라우저 저장 기능을 그대로 쓴다.

### 첫 방문 안내

`guide(id, title, steps, host)`의 각 단계는 제목·설명·선택적 대상 selector를 선언한다. 프레임은 앱 내용을 알지 못한다. 처음 표시한 안내는 이전·다음·시작하기·건너뛰기를 제공하며 완료된 버전만 계정에 저장한다(그래서 로그인한 사람에게만 뜬다). Escape는 이번 방문만 닫는다. 저장 실패는 완료로 표시하지 않고 재시도를 제공한다. 다시 여는 자리는 한 곳, 사이트 머리글 내 메뉴의 '사용 안내'다 — 화면마다 단추를 따로 붙이지 않는다(`host` 인자는 첫 판의 호출을 위해 받기만 한다). Tab은 안내 안에서 순환하고 닫힌 뒤 초점을 복원한다. 페이지 전환 시 반환된 정리 함수를 실행한다.

## 2. 계정 설정과 실패 처리
<!-- sec:s2 basis: U2 U4 A4 A6 E1 U9 E15 E16 -->

`Prefs`는 언어·테마·시작 페이지, 켠 앱의 순서, 위젯 배치와 크기, 카탈로그에서 본 앱, 완료한 안내, 모양을 저장한다.

```ts
interface Prefs {
  lang: string;
  theme: 'auto' | 'light' | 'dark';
  start: string;
  apps: string[];
  home: { app: string; widget: string; size?: string }[];
  homeCustomized?: boolean;
  seen: string[];
  guides?: string[];
  look: {
    palette?: string; corner?: string; type?: string; size?: string;
    columns?: number; image?: string; accent?: string;
    colors?: Partial<Record<'light' | 'dark', Record<string, string>>>;
    radius?: number; imageBlur?: number; imageDim?: number;
  };
}
```

설정이 없는 계정은 사이트 파일의 기본 앱으로 시작한다. 저장된 빈 앱 목록은 그대로 유지한다. 직접 편집한 홈이 빈 경우에도 기본 실행기를 되살리지 않는다. 카탈로그의 `seen`과 안내의 `guides`는 서로 다른 목적이다.

프레임은 me와 계정 설정을 읽은 뒤 테마·언어를 적용한다. 설정 쓰기는 순서대로 처리하며, 실패한 값을 화면이나 첫 칠 캐시에 저장하지 않는다. 저장된 적 없는 계정은 키 목록을 먼저 조회한다. 이전의 `hidden/order`는 읽을 때 호환한다.

## 3. 앱 목록과 이동 주소
<!-- sec:s3 basis: U2 U3 A4 A7 E19 -->

앱 목록은 검색·태그, 추가한 앱의 타일, 추가할 수 있는 앱의 카드로 구성한다. 추가는 계정에 저장된 뒤 메뉴와 홈에 반영한다. 타일의 메뉴는 앱 정보와 빼기를 제공한다. 검색과 태그는 주소에 남는다.

카드의 정규 이동 주소는 메뉴 주소, 첫 링크, 앱 정보 경로 `/app/<id>` 순서로 정한다. SMB나 MCP처럼 연결 정보만 있는 앱도 헤더와 홈에서 정보 화면으로 이동할 수 있어야 한다. 상세 페이지가 정규 목적지인 경우 자기 자신을 다시 여는 버튼은 표시하지 않고 연결 주소와 복사 동작을 보여준다. 외부 클라이언트 URI와 명령은 웹 경로 검사와 구분한다.

새 앱 표시는 카탈로그에만 두며, 앱별 위젯·연결 주소·상세 설명은 정보 화면에서 찾는다.

## 4. 홈과 위젯 크기
<!-- sec:s4 basis: U1 U4 A4 A6 E1 E15 E17 E20 -->

앱은 위젯의 id·제목·설명·모듈·기본 크기를 선언한다. 서버는 중복 id, 없는 모듈, 잘못된 크기와 설명을 검사하고 me에 내린다. 크기 표는 서버 선언 하나에서 오며 프레임이 복사본을 갖지 않는다.

홈은 직접 배치한 위젯 또는 켠 앱의 실행기를 그린다. 제목 끌기는 순서를, 모서리 끌기는 선언 크기를 바꾼다. 메뉴에도 크기·앞으로·뒤로·빼기가 있고 키보드 Alt+방향키·Delete를 지원한다. 변경은 배치별로 저장한다. 빈 홈은 앱 추가로 연결한다.

현재 크기는 1×1·2×1·1×2·2×2다. 설정의 열 수는 가능한 최대 요청이며 작은 화면에서는 내용의 최소 폭을 보장하도록 줄어든다. 물리적 폭이 부족한데 요청한 열 수를 강제로 유지하지 않는다. 위젯 고르기는 제목·설명·크기와 실제 모듈 미리보기를 제공한다. 사용 안내는 이 조작을 재생하며 홈의 작업을 대신하지 않는다.

모듈 계약은 `default(host, ctx)`이고 ctx는 프레임·설정·언어·테마·이동·API·앱·위젯, 그리고 칸의 크기(`ctx.size`: 사람이 준 크기, 없으면 선언 크기)다. 위젯 로딩 실패는 해당 앱 실행기로 대체한다.

### 4.2 위젯의 부품: PIM 화면

위젯은 자리표시가 아니라 앱의 내용을 한눈에 보이는 화면이다: 항목을 하나씩 늘어놓고(목록), 그 상태를 숫자와 작은 그림으로 요약한다. 모든 위젯이 같은 부품으로 그리므로 읽는 법과 누르는 법이 같다. 부품은 `site.js` 가 내고(`web/frame/widgets.ts`), 모양은 `widgets.css`(토큰만)다.

| 부품 | 그리는 것 |
|---|---|
| `items(rows 또는 groups, none, more)` | 한 줄에 하나: 앞머리(시각, 체크), 표(데이터가 주는 색 — 캘린더의 색), 글과 둘째 줄, 끝(날짜·수·꼬리표). 줄은 지난 것(흐리게)·지금·다음일 수 있다. 묶음은 제목과 수 아래. 남는 것은 'n개 더' 링크 |
| `groupHead(title, aside)` | 묶음의 제목과 수(할 일 목록처럼 자기 줄을 그리는 편집기도 이것으로 묶는다) |
| `stats([{n, label, tone}])` | 머리의 숫자들(일정 3 · 오늘 마감 1 · 지남 2) |
| `meter(value, max, label)` | 전체 중 끝낸 만큼 |
| `dayStrip(days)` | 이어진 날들: 요일·날짜·그날의 수(그날 일정의 색 점), 오늘 표시, 날마다 링크 |
| `monthGrid({year, month, counts, picked, pick, move})` | 한 달(월요일 시작, 캘린더와 같다): 날마다 수만큼의 단계, 오늘 테두리, 고른 날, ‹ › |
| `bars(list)` | 이름별 수를 가장 큰 것에 대한 막대로(볼트의 태그) |
| `activity(days, label)` | 날마다의 수를 기둥으로(최근 14일 고친 노트) |
| `fit(ctx)` · `ago(t)` · `dayKey(d)` | 칸이 담는 목록 줄 수(칸의 행 × theme.css `--cell-items`), '3시간 전', 'YYYY-MM-DD' |

단계(날·막대의 짙기)는 가장 큰 수에 대한 비로 셋이다. 데이터가 주는 색은 `--mark`, 비율은 `--v` 로만 요소에 얹는다(CSSOM). 사이트의 위젯 모듈(`web/widgets/*.ts`)은 목록 마크업을 직접 쓰지 않고 이 부품으로 그린다(검사가 지킨다). 앱 저장소의 위젯(수식 플립플롭의 작업판)도 같은 부품을 쓸 수 있다.

## 5. UI 생성 규칙과 감사
<!-- sec:s5 basis: U1 U4 A4 A12 U9 E15 E17 E19 E20 H10 -->

| 원칙 | 적용 |
|---|---|
| 요소의 의미 | 이동은 링크, 실행은 버튼, 켜고 끄기는 스위치, 선택은 select·칩 |
| 객체의 자리 | 일정·노트·위젯의 조작은 해당 객체의 메뉴·직접 조작에서 제공 |
| 실패 후 복구 | 원인과 재시도·취소를 같은 자리에서 제공하고 입력을 보존 |
| 테마의 범위 | 배경뿐 아니라 버튼·입력·탭·모달·상태·글꼴도 같은 토큰을 사용 |
| 안전한 치수 | 둥글기와 최소 폭을 부품 크기에 맞춰 제한. 큰 글자에서 줄바꿈 |
| 실제 기능 | 저장·새로고침·실패·탐색 취소를 확인. 버튼 존재는 동작 완료의 근거가 아님 |
| 안내 | 첫 방문에 시작법을 설명하고 재열기·키보드·실패 저장 상태를 갖춤 |
| 검증 범위 | 기본값 하나의 스크린샷이나 모의 앱을 전 앱의 통과로 해석하지 않음 |

`pageHead`는 제목과 탭, `section`은 작업 내용, `help`는 필요한 보충 설명의 자리다. 안내 설명은 별도 오버레이에 둔다. 글자가 커져 높이가 늘면 헤더를 줄바꿈하고 좁은 화면에서는 본문을 가리지 않도록 한다.

현재 확인한 결함과 경계는 별도 UI/UX 리뷰 보고서의 범위표에서 관리한다. 사이트 공통 화면, 실제 WordGenerator, 외부 앱의 일부 코드 검사를 같은 검증으로 합치지 않는다.

## 6. 캘린더와 노트
<!-- sec:s6 basis: U2 A3 A5 A8 A9 E14 E20 -->

캘린더·프로젝트·노트는 새 계정의 기본 앱이다. 캘린더는 개인·프로젝트 달력을 겹쳐 보고 월·주 보기, 날짜 패널, 일정 편집, 할 일과 기기 연결을 제공한다. 홈에는 오늘·다가오는 일·할 일을 기여한다.

노트는 등록한 볼트를 트리·검색으로 열고 같은 자리에서 읽고 편집한다. 저장하지 않은 변경은 탐색 전에 확인하며, 늦은 검색·노트 응답이 새 상태를 덮지 않도록 한다. 홈에는 최근 노트와 Home 노트를 기여한다. 서비스·권한·API의 상세 계약은 `apps-vault-calendar.md`·`calendar.md`·`vault.md`에 둔다.

## 7. 검증 기준
<!-- sec:s7 basis: C1 U1 U2 A1 A2 E15 E17 E20 -->

수정 전에 요구별 통과 조건을 선언한다. 공유 부품의 색은 토큰에서 오며 TypeScript와 선언·번역 검사에 신규 오류가 없어야 한다. 저장된 사용자 선택과 권한별 경로를 유지한다.

브라우저 검증은 새 계정·빈 홈·앱 추가/제거·위젯 이동/크기 저장·테마와 첫 칠·편집 저장/취소·실패 재시도를 포함한다. 안내는 최초 표시, 완료와 건너뛰기 저장, Escape 비완료, 다시 보기, 초점과 Tab 순환을 확인한다.

작은 화면과 큰 글자를 함께 사용해 가로 넘침 1px 이하, 활성 본문 대비 4.5 이상을 검사한다. 선언된 팔레트 외에 두 모드의 사용자 지정 표면·채움, 배경 흐림·어둡기를 검사한다. 앱 자체 부품의 모달·탭도 실제 빌드로 검사한다.

변경은 공유 저장소의 복사본에서, 공유 저장소가 체크아웃한 브랜치의 HEAD 에서 판 주제 브랜치 위에서 검증하고, 기준 커밋과 시험 결과를 커밋 본문에 남긴다. 코드 검증과 운영 배포·실제 사용자 관측은 별도로 보고한다.

## 8. 작업과 반환 절차
<!-- sec:s8 basis: A2 E13 H9 U11 -->

공유 작업 트리와 거기 체크아웃된 브랜치는 건드리지 않는다: 그 안에서 checkout·직접 수정·commit 을 하지 않는다. 저장소를 복사(clone)해, 공유 저장소가 체크아웃한 브랜치의 HEAD 에서 주제 브랜치(`topic/<주제>`)를 파고 그 복사본에서 변경한다. 공유 작업 트리에 미커밋 변경을 쌓아 두지 않는다 — 남아 있는 것은 어느 작업의 것인지 가려 그 주제의 브랜치로 묶는다.

절차는 요청 원문과 기존 상태 확인, 누락 요구와 완료 기준, 구현, 실패 원인 수정, 실측 증거 기록, 문서 변경 목록과 동기화, 시험, 주제 브랜치 제출 순서다. 기존 규칙을 읽지 않은 오류를 새 규칙 추가만으로 처리하지 않는다. 수정 결과가 원래 요구와 대응하는지 마감 전에 대조한다.

코드·생성 프레임·타입·검증 스크립트·문서를 한 주제의 브랜치에 의미 단위의 커밋으로 함께 싣고, 그 브랜치만 공유 저장소로 push 한다(외부 원격으로의 push, force push, 브랜치 삭제는 하지 않는다). 커밋 본문에 근거와 시험 여부를 적는다. 머지와 배포는 사용자가 한다 — 머지되지 않은 브랜치를 웹사이트에 반영됐다고 보고하지 않는다. 옛 방식으로 돌려준 패치 묶음(`/Workspace/_patches/`)은 이력으로 남는다.

## 10. 남은 확인
<!-- sec:s10 basis: U1 U2 U3 U4 A5 U9 E14 E20 -->

외부 equation-sandbox는 공통 테마를 불러오고 색에 토큰을 사용하지만 자체 모서리·수학 글꼴 값이 남아 있다. 사이트 회귀의 수식 앱 페이지는 프레임 모의 페이지이므로 해당 앱 전체의 테마·작업판 동작 통과를 뜻하지 않는다. 별도 저장소의 현재 작업과 대조한 뒤 같은 범위의 실제 빌드 검증이 필요하다.

운영 서버 적용, 실제 사용자 환경에서의 재현 확인, 외부 이미지의 SSO CSP, 실제 SMB·MCP 클라이언트 접속은 여기서 완료 판정하지 않는다. CodeMirror·git 이력·그룹 볼트 같은 별도 기능은 해당 설계 문서에서 추적한다.

## 14. 교정본 검증과 반환
<!-- sec:s14 basis: U9 U11 A2 E13 E14 E15 E16 E17 E18 E19 E20 H9 H10 -->

2026-11-07 복사본에서 포털 테스트 150개와 WordGenerator 단위 테스트 21개가 통과했다. 추가 링크 수정 후 프레임·번역·사이트 계약 65개가 통과했다. 사이트 기존 흐름 182단계, 두 모드의 본문 대비와 123개 배치 쌍, 큰 글자·둥글기·폭의 63조합을 확인했다.

실제 WordGenerator는 320·768·1100px, 밝음·어두움, 둥글기 0·100, 125% 글자와 네 탭·어휘 관리 모달의 60조합에서 가로 넘침이 없고 측정한 활성 본문 대비 최솟값은 6.66이었다. 사용자 지정 색과 이미지 필터, 안내의 저장/실패/초점, 초안 저장 후 다시 불러오기, 연결 정보 앱의 헤더·홈 이동도 검사했다.

검증 환경은 Node 22.23.4와 Chromium headless, 한국어, 인메모리 서비스 모의와 TestClient다. 임의 키워드의 내용에 기대는 단언은 없다. 검사 결과는 이 환경과 입력 범위에서 교정본을 뒷받침한다.

반환 위치는 `/Workspace/_patches/site-frame/ui-ux-20261107/`다. 현재 공유 파일 기준 증분 패치, 리뷰 보고서, 검증 로그·측정 JSON·화면과 기준 해시를 둔다. 선행 변경이 이미 공유 트리에 들어간 사실은 이 패치를 다시 적용할 이유가 아니며, 이번 신규 코드는 적용 전 산출물이다. 적용 기준과 검증 로그는 묶음의 manifest에서 확인한다.
